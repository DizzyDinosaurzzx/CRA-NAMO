# CA-NAMO

**在可移动障碍物之间导航。** 机器人要从起点走到终点，路被家具挡着。绕路多走冤枉路，搬开要费力气——哪个划算？

CA-NAMO 把这两件事换算成同一个单位（焦耳），于是"绕还是搬"变成一道能直接比大小的算术题：

```
J  =  λ · D  +  W
      ╰──┬──╯   ╰┬╯
         │       └── 搬运做功 = Σ(摩擦力 × 移动距离)
         └────────── 行驶做功 = 等效行进阻力 λ × 行驶距离 D
             （D 含原地转弯：转弯角度按机器人半径折算成等效弧长一并计入，
              和搬运项里障碍物自转按同样方式折算是同一套物理类比）
```

难点在于机器人**事先不知道**每个障碍物有多重。它从材质名（"钢制货架"、"泡沫箱"）用 LLM 估一个推动阻力，边走边看边重新规划；一旦真碰上了，就换成真值重新算账。

## 快速开始

```bash
pip install -r requirements.txt
cd CA-NAMO

python main.py                          # 默认场景 two_doors
python main.py --scenario maze_doors    # 换场景（清单见下）
python main.py --lambda 1750            # 调大 λ：走路更贵，机器人更愿意搬东西
python main.py --time-importance 1      # 只求最快，不计能耗
```

每次运行产出两个文件：

- `img/summary_<场景>.png` — 终态一张图：机器人走过的走廊、障碍物的起止位置
- `img/frames_<场景>.gif` — 全过程动图，一步一帧

## 三条核心规则

理解这三条就理解了整个系统。

### 1. 距离和力气用同一把尺子量

`difficulty` 不是一个抽象分数，而是**推动这个障碍物要克服的滑动摩擦力**，单位牛顿：

```
difficulty = μ · m · g = (μ·ρ) × V × g       V = l×d×h（包围盒体积）
```

λ 也是牛顿（机器人的等效行进阻力，默认 350 N）。两者量纲相同，所以 `λ×距离` 和 `力×距离` 都是焦耳，能相加。这是整套方法能成立的前提。

> λ=350 是标定值，不是机器人的裸滚阻。取这么大是为了让"绕路 vs 搬开"落在有意义的区间——障碍物阻力是几十到几万牛顿量级，λ 要是取 1，绕几百米都比搬一米便宜，问题就退化成普通路径规划了。

原地转弯同样要做功：机器人半径处的一点沿弧线扫过的距离，按同一个 λ 折算成焦耳，直接并入 D。这和搬运项里"障碍物自转按平均旋转半径折算成距离"（见下方规则 2）是同一套类比——转弯不是免费的，纯能量目标（`time_importance=0`）不该对它视而不见。

### 2. 搬东西时，机器人必须一直贴着它

障碍物不会自己动。移动它的**全过程**中机器人都得和它保持物理接触，所以机器人自己也要走这一段路——绕过去够到它、贴着它一起走、放手后回到路网。这三段全部按 `λ×距离` 计入 D。

接触点可以落在障碍物周边**任意位置**，因此推、拉都合法，方向不受限制。

```
        ┌──────────┐                    ┌──────────┐
     ●  │ obstacle │  ──►            ●  │ obstacle │  ──►
     ↑  └──────────┘                    └──────────┘  ↑
    机器人在后面推                          机器人在前面拉
```

这条规则不是可选项——见[引入时的实测对照](#接触模型带来了什么)，当年就是靠这组数据证明它会真的改变决策，不只是多记一笔账。

### 3. 只知道看得见的东西

机器人维护两套世界：`self.world`（真实）和 `self.belief`（它以为的）。规划器**只能看 belief**。

每走一步重新感知一次，发现新障碍物立刻重规划。难度估计值只用来做决策；一旦发生物理接触（撞上或搬动），真值立即写入 belief，账目永远按真值结算。

**估计错了只会让决策次优，不会让账算错。**

## 选路目标：省力，还是求快

J 是这趟**花了多少**，但不一定是选路时**唯一该看**的东西。`time_importance`（记作 `w`，0~1）把任务时间也拉进来一起决定走哪条路：

```
C = (1-w) · J  +  w · P · T          P = λ · v_max = 280 W
```

- `w = 0` — 只看能耗，和这个旋钮存在之前**逐位相同**
- `w = 1` — 只求最快，能耗完全不看
- 中间 — 两者按比例折中

**P 不是又一个要标定的常数**，它就是机器人巡航时的功率（λ [N] × v_max [m/s]）。用"一秒钟行驶要花多少焦耳"来给一秒钟定价，于是两项自然可比。这样定价还有个漂亮的副作用——对普通行驶，混合项**恰好抵消**：

```
(1-w)·λd  +  w·(λv)·(d/v)  =  λd
```

所以 `w` 完全不动"走路"的价格，它只动**搬东西**的价格。这正是它该管的那笔账：能量在乎东西有多重，时钟不在乎，时钟在乎的是机器人握着它的时候只能爬 0.25 m/s，还要花 4 秒抓放。

一个障碍物"值得为它绕多远"，随 `w` 变化（λ=350，搬运行程 0.6 m，移动 3 m）：

| `w` | 轻物（W=10 J） | 重物（W=20000 J） |
|---:|---:|---:|
| 0 | 绕 0.6 m 就不值 | 绕 57.7 m 都值得 |
| 0.5 | 绕 2.9 m | 绕 31.4 m |
| 1 | 绕 5.1 m | 绕 5.1 m ← 时钟不认重量 |

**两个必须知道的边界：**

1. **规划期的时间是估计值，执行期的时间才是真的。**规划器按巡航速度估算，不算加减速；转向的**能耗**任何 `w` 下都恒定计入（转弯本来就要做功，见下方"距离和力气用同一把尺子量"），只有转弯的**时间**项才只在 `w > 0` 时按真实剖面额外计一笔（`cost.search_turn_cost`）。这和"用估计难度规划、用真实难度结算"是同一套路数。报出来的 `Robot motion time` 永远来自执行器。

   > 这条边界不是凭空定的：`corridor` 场景实测过，转弯能耗不进 J 的旧版本里 `w=0/0.5/1` 分别得到 J=14637.4/14121.3/14121.3——`w=0` 反而更差，因为 A\* 对转弯完全无感，分支限界剪掉了本该更省的推障碍物方案。补上转弯能耗之后三档**完全一致**（J=16065.7817），`w=0` 也收敛到了原来只有 `w>0` 才能找到的推法。
2. **`w` 调大不保证实测时间一定变小。**这是个在线重规划循环，每 cycle 只执行一条边就重新感知重规划，整条实际轨迹是几十个 plan 的首边拼起来的，不是任何一次搜索的最优解。实测见[下面的对照](#时间权重的实测对照)。

## 决策循环

```
      ┌──── 感知 ────┐         perception.py   看见什么，记进 belief
      │              ↓
      │           规划          search.py      A* 搜索，对被挡住的边算"搬开要多少钱"
      │              ↓
      │           执行          executor.py    走一步，或搬一个障碍物
      │              │
      └──── 有新发现？重来 ──────┘
```

每个 replan cycle 只执行规划路径的前 `step_execute_edges` 条边（默认 1），然后重新感知。碰撞或新发现立即触发重规划。

## 地图也会自己变

前面三条规则默认"障碍物不会自己动"——它挪不挪，只取决于机器人搬不搬它。这不总是对的：巡逻的叉车、靠近才让开的门、被别人重新摆放的货架，都是地图本身在变，跟机器人的动作无关。

`drift.py` 给 `MovableObstacle` 加了一个可选的 `drift` 字段，挂上之后它就会按某种策略自己走。`self.world`（真实）和 `self.belief`（信念）那套分离完全不用改——机器人是否知情仍然只取决于会不会真的看见它，"部分可观测"的规则照旧成立。不挂 `drift` 的障碍物（也就是全部原有场景）行为和这个模块不存在时逐位相同。

三种触发方式最终都归到同一个接口：给定经过的时长和当前世界快照，返回这一步的新位姿，或者"不动"。

```python
drift.scripted(keyframes, loop=True)                   # 按时刻表跑，比如巡逻
drift.event(condition, keyframes, loop=False)          # 触发前不动，触发后按脚本跑一次
drift.reactive(rng_seed, speed, bounds, avoid_radius)   # 每 tick 自己决定往哪走
```

`event()` 内部就是把"触发时刻"当新的时间原点交给 `scripted()` 插值，不是另一套逻辑；`reactive()` 是唯一真正需要每 tick 自己做决策而非查表的一种，用 `rng_seed` 播种保证同一场景每次跑结果一致。

驱动这一切的是**一个统一仿真时钟**：机器人自己产生的物理耗时（行走、转向、抓放、贴身护送）才会推进它；A\* 搜索和 LLM 调用花的**思考时间不算数**——只用来衡量算法本身，不代表世界在动，和"时间不进 J"是同一种"分开量、分开报"的原则。感知触发的粒度、GIF 每帧的播放时长，用的也是这同一个钟，配置好的障碍物速度和 GIF 里看起来的速度天然对得上。

实现细节、参数表和踩过的坑见下文「各子系统 → 自主运动与统一仿真时钟」；专门用来快速验证的最小场景是 `scenarios/drift_demo.py`。

## 命令行

```
python main.py [--scenario NAME] [--lambda VALUE] [--strategy NAME]
               [--time-importance W]
               [--forward-penalty V] [--no-llm-order] [--frames]
```

| 参数 | 说明 |
|---|---|
| `--scenario` | 场景名，默认 `two_doors` |
| `--lambda` | 等效行进阻力 λ [N]，默认 350。越大越倾向搬东西 |
| `--strategy` | `normal`（默认，最优 J）/ `shortest`（忽略 W，走最短） |
| `--time-importance` | 时间在选路中的权重 `w`，0~1，默认 0。0=只看能耗，1=只求最快 |
| `--forward-penalty` | 落点前向偏置，默认 2.0；`0` = 对搬运方向不做任何偏好 |
| `--no-llm-order` | 关掉 LLM 排序偏置（只影响搜索展开顺序，不影响结果） |
| `--frames` | 保存过程动图（默认已开） |

> 2026-08-21 起规则 2（机器人必须贴身护送）**没有开关**了——`--no-contact` 和
> `config.contact_required` 已经从代码里彻底删掉，贴身搬运是唯一的搬运模型。

两种策略只改变 **A\* 搜索时怎么算边的代价**，J 的计算公式和执行阶段的结算方式完全一致。

## 输出怎么读

```
Success                : True   (Reached goal.)
Total cost J           : 14,367.2083
motion lambda*D        : 14,357.0904   # λ=350 × D=41.02 m（含转弯等效弧长）
  of which in contact  : 1,052.3038    # 其中 3.01 m 是贴着障碍物走的
obstacle work W        : 10.1178
Obstacles moved        : [1]
Replan cycles          : 70
A* expansions          : 52,040
LLM calls              : 0  (mode=deepseek)
------------------------------------------------------------
Robot motion time      : 95.73 s   (1m 35.7s)   (v=0.8/0.25 m/s free/contact, a=0.5/0.2 m/s^2)
  of which handling    : 29.40 s   (gripping, escorting and backing out)
Decision compute time  : 16.94 s   (70 replans, measured wall clock)
Total mission time     : 112.68 s   (1m 52.7s)
```

（`two_doors` 场景，`time_importance=0`，2026-08-21 转弯能耗并入 J 之后重新跑的数字）

**代价那半张表**

- **J** = λD + W，总代价
- **motion λ×D** — 行驶做功。除以 λ 得到总行驶米数
- **of which in contact** — 上一行里属于"搬运期间机器人自己走的路"的部分（进场 + 贴着走 + 出场）
- **obstacle work W** — Σ(**真实** difficulty × 实际移动距离)
- **LLM calls** — 材质全部命中锚点表时为 0，即使处于 deepseek 模式

**时间那半张表**

任务总时长拆成两块，**分开报，也报合计**：

- **Robot motion time** — 机器人物理跑完这条路要多久，**仿真值**。由 `timing.py` 按速度/加速度上限从执行器实际走过的每一段折线算出来
- **of which handling** — 上一行里花在障碍物上的部分：抓取/松手的固定开销、贴着障碍物走的那段、以及事后回路网
- **Decision compute time** — 决策计算时间，**实测墙钟**，就是每个 cycle 里 `planner.plan()` 的耗时之和（A\* 搜索 + 若真打了 LLM 也算在内）
- **Total mission time** — 上面两者之和。规划与执行在本系统里是严格串行的（走一步 → 重新感知 → 重新规划），所以直接相加

> 时间**不进 J**——J 始终是纯能量账，两个数分开量、分开报。时间要不要参与**选路**，由 `time_importance` 单独控制，见[选路目标](#选路目标省力还是求快)。默认 `w=0` 时速度参数只影响报出来的秒数，不影响任何决策。

## 代码地图

依赖图**无环**，下面的顺序就是依赖顺序，从上往下读：

| 模块 | 职责 |
|---|---|
| `config.py` | 所有可调参数 |
| `geometry.py` | 纯几何原语（矩形、凸包、Minkowski 和、SAT、角度归一）。**不 import 任何本地模块**，是依赖图的根 |
| `obstacle.py` | `StaticObstacle` / `MovableObstacle` |
| `drift.py` | 障碍物自主运动策略（脚本化/事件触发/反应式），与机器人推拉完全无关 |
| `cost.py` | **J = λD + W 的唯一出处**；以及搜索目标 `C=(1-w)J+wPT` 的混合 |
| `timing.py` | **任务时间的唯一出处**：差速盘的梯形速度剖面，把执行器走过的折线折算成秒 |
| `se2_planner.py` | SE(2) 网格 Dijkstra：只回答"这个物体能不能挪过去、怎么挪" |
| `manipulation.py` | 仿真世界 ↔ SE(2) 规划器的适配层：扫掠体、路径验证、规划器缓存 |
| `contact.py` | 接触式搬运：握持点采样 + DP，算机器人贴着障碍物走的轨迹 |
| `roadmap.py` | 增广路网 + 三层机器人自由空间 |
| `perception.py` | 感知、遮挡、碰撞检测、信念维护 |
| `llm_difficulty.py` | DeepSeek 难度估计 + 离线启发式回退 |
| `search.py` | A* 分支限界搜索 |
| `executor.py` | 在线"规划-执行-感知-重规划"主循环 |
| `viz.py` / `main.py` | 渲染 / 命令行入口 |
| `scenarios/` | 场景定义 |
| `bench/` | LLM 精度基准（`llm_accuracy.py`、`llm_dataset.py`、`llm_test_out/`） |

**三条硬约束**，破坏了就会重新变乱：

1. `geometry.py` 不许 import 本地模块——它是无环的根
2. 除 `cost.py` 外，任何地方都不该再乘 λ 或乘 `difficulty`
3. 除 `timing.py` 外，任何地方都不该再拿距离除以速度

### 命名前缀

| 前缀 | 指什么 |
|---|---|
| `manip_` / `move_` | 把障碍物挪走这件事本身（推拉皆可） |
| `se2_` | 障碍物**自己**那条路径怎么搜 |
| `contact_` | 机器人握住障碍物的那条轨迹 |

旧代码通篇叫 `push`，那是"只能推"时代的遗留词，已统一改掉。**`llm_difficulty.py` 的 prompt 文本和 `bench/` 刻意没动**——改了会让已发表的基准结果不可比。

## 各子系统

### 增广路网（`roadmap.py`）

- **只建一次**，基于静态墙体。`grid_step=0.3m` 均匀采样节点，`conn_radius=0.6m` 连接（two_doors 约 6000 节点 / 34000 边）
- 可移动障碍物**不改变图结构**，只标记哪些边当前被挡住——变成"付费解锁"的边
- 三层自由空间，名字按腐蚀量区分，用错了很难发现：


  | 集合 | 腐蚀 | 用途 |
  |---|---|---|
  | `static_free` | 无 | 工作空间减去墙 |
  | `free_eroded` | `robot_radius` | 机器人圆心能待的地方，建路网用 |
  | `free_eroded_tol` | `robot_radius − contact_clearance` | 同上但松一丝，握持点用 |


  第三层是必要的：贴着墙的障碍物，其握持点正好落在第二层的边界上，会被浮点误差判死。

### 任务时间模型（`timing.py`）

J 回答"这趟花了多少能量"，这一节回答"这趟花了多少时间"。两个数**分开量、分开报**，时间永远不进 J。至于时间要不要参与选路，那是 [`time_importance`](#选路目标省力还是求快) 的事——默认 `w=0` 下改速度参数只改变报出来的秒数，不改变任何决策。

```
T = T_motion（仿真）+ T_decision（实测墙钟）
```

**运动学假设：差速驱动的圆盘 —— 原地转向，然后直线行驶。**所以一条折线的耗时是

```
Σ 直线段  trapezoid(段长, v_max, a_max)
+ Σ 拐角  trapezoid(|转角|, ω_max, α_max)
```

`trapezoid` 就是标准的加速—匀速—减速剖面，路太短跑不到 `v_max` 时自动退化成三角剖面：

```
d ≥ v²/a :  t = d/v + v/a
d < v²/a :  t = 2√(d/a)
```

三个实现要点：

- **共线段必须先合并再套剖面**。路网 `grid_step=0.3m`，一条直走廊被切成几十跳；逐跳算剖面等于让机器人每 0.3 m 刹停一次，数字就没意义了。合并后 two_doors 的 36.5 m 只有 11 段直线 + 10 次转向
- **贴身搬运用第二套更慢的上限**（`*_contact`）：机器人正压着一个不能让它打滑的负载，开得和转得都比空载温柔得多。默认 0.25 m/s vs 空载 0.8 m/s
- **倒车不计转向**。撞上东西退回原节点这种情形，差速盘直接倒着开回去，要刹停但不用掉头

| 参数 | 默认 | 含义 |
|---|---:|---|
| `v_max` / `a_max` | 0.8 / 0.5 | 空载巡航速度 [m/s] 与线加速度 [m/s²] |
| `w_max` / `alpha_max` | 1.5 / 2.0 | 空载原地转向角速度 [rad/s] 与角加速度 [rad/s²] |
| `v_max_contact` / `a_max_contact` | 0.25 / 0.20 | 贴住障碍物时的同名上限 |
| `w_max_contact` / `alpha_max_contact` | 0.50 / 0.80 | 同上，转向 |
| `grip_time` | 2.0 | 抓取一次的固定开销 [s]，松手再记一次 |

时间的累加口和代价的累加口是**同一个** `executor._charge_walk`，所以"走了多少米"和"走了多久"不可能对不上账。

**规划期的估计值**（只在 `w > 0` 时用得上，`timing` 里的 `drive_seconds` / `removal_seconds`）比这套模型粗：按巡航速度算，不含加减速。规划器在给一条**可能根本不会走**的边定价，而且不知道机器人到那儿时朝哪边——朝向取决于路线，要算就得把搜索状态从"节点"扩成"(节点, 朝向)"。粗估的好处是它天然是执行期真值的**下界**，A\* 启发式因此保持可采纳。

转向是唯一的例外，它**按真实剖面精确计价**（`cost.search_turn_cost`），因为不计的话代价太大：搜索会看中一条距离略短、却多出十几次"刹停—掉头—起步"的路线，省下的米数远抵不上多花的秒数。实测过一版没有它的：`w=0.25` 时直线段从 4 段炸到 15 段、多出 12 次转向共 15.4 s，把省下的搬运时间全吃掉了。

转向要看**前一条边**，而每条边的代价是按边缓存的，看不到这个。所以它算在 A\* 展开循环里，用 `parent` 记录的那个前驱；`g_best` 仍然只按节点索引，不扩成 (节点, 朝向)——和"用边中点代替两个端点"是同一类近似。**起点那一跳单独喂真实朝向**（`executor` 把 `timer.heading` 传给 `planner.plan`），这一跳最要紧：`step_execute_edges=1`，每个 cycle 只有首边会被真的走，整条实际轨迹就是几十条首边拼出来的。

### 自主运动与统一仿真时钟（`drift.py`）

「地图也会自己变」讲了动机，这里是实现。`MovableObstacle` 多一个可选字段 `drift`；`perceived_copy()` 不带这个字段——belief 侧永远不知道障碍物真实的运动策略，只能靠一次次 `perceive()` 追上真值，和 `difficulty` 在信念侧置 `NaN` 是同一个原则。

**统一时钟怎么接进来**：`executor._tick(dt)` 挂在三处——`_charge_walk`（覆盖全部行走/转向）、`_execute_move` 里的 `timer.grip()`、`timer.transport()`。`dt` 一律取 `self.timer.elapsed` 前后差值，不另开一条时间线。规划耗时（含可能的 LLM 调用，最长可达 ~80s）**刻意不接进来**——世界在机器人思考的时候不会跟着漂移，思考时间只用于衡量算法本身。这个决定的直接好处：能触发 `_tick` 的 Δt 全部来自机器人自身动作，天然被 `grid_step`/`se2_cell` 卡在很小量级，不需要额外的有界子步切分逻辑防止障碍物"跳步穿墙"（`config.wait_on_block_s` 那条等待除外，见下）。

**三种触发方式**：

| 函数 | 用途 | 关键参数 |
|---|---|---|
| `drift.scripted(keyframes, loop)` | 按 `(仿真时刻, 位姿)` 时刻表分段线性插值；朝向按 `geometry.wrap_dtheta` 走最短转角，不直接对存储角插值 | `loop=True` 超出末尾按周期折返 |
| `drift.event(condition, keyframes, loop)` | 触发前不动；`condition(obs, state)` 首次为真时记下触发时刻，之后把 `keyframes`（相对触发时刻）交给 `scripted()` | 内建条件 `robot_within`/`obstacle_removed`/`after`，可用 `all_of`/`any_of` 组合 |
| `drift.reactive(rng_seed, speed, bounds, avoid_radius)` | 每 tick 在 `bounds` 内随机挑目标点匀速前进，到达就重新采样；采样时跳过会让目标点落进机器人 `avoid_radius` 的候选 | 只是"尽量不主动凑近"，不是物理碰撞保证，真撞上仍走 `executor` 现有碰撞检测兜底 |

**感知触发**（`config.perc_step` / `perc_time_step`，默认都是 `inf` 即关闭）：距离阈值挂在 `_set_robot`（真正挪动位置时才有增量，取景精确），时间阈值挂在 `_tick`（覆盖抓取/等待期间原地不动但时间在流逝的情况）。

**等待动作**（`config.wait_on_block_s`，默认 0 关闭）：机器人**盲撞上一个尚未感知到的 drift 障碍物**时，先按 `wait_substep_s` 为步长原地等一会再重规划，而不是立刻重规划绕路。**触发条件很窄**——只要障碍物提前在感知半径内可见，机器人早就绕着它当前位置走了，根本没机会盲撞，这个钩子就不会触发；多数场景默认 `R_perc=10` 基本覆盖全图，实测中它确实很少触发。没有做成 A\* 的新动作类型——那需要给搜索加时空维度去预测 drift 的未来轨迹，代价和风险远超这次改动范围。

**GIF 也用同一个钟**：`viz._frame_durations` 按相邻帧 `motion_time`（同样不含 `plan_time`）差值算每帧播放时长，`gif_speed` 是相对仿真时间的播放倍率，`gif_fps`/`gif_max_frame_s` 分别给单帧时长设下限/上限。

**机器人搬运和 drift 撞在一起怎么办**：贴身搬运一个挂了 `drift` 的障碍物期间，`executor._active_manip_oid` 会暂停这个障碍物自己的运动，不然两条写入路径会打架。但松手之后它立刻恢复自己的时刻表——`scripted()` 按**绝对仿真时刻**查表，不管机器人刚把它放在哪，下一个 tick 就会跳回时刻表说它现在该在的位置。这意味着"推开一个正在巡逻的障碍物"往往**不是一次性的**：机器人可能得反复推它，因为它会自己飘回挡路的地方。这是设计选择的直接后果，不是 bug；如果想要"推开就定住"的语义，需要另一种"被碰过就相对当前位置重新计时"的策略，目前还没做。

参考场景：`scenarios/drift_demo.py`——20×8 单走廊+2m 门，三个障碍物各演示一种触发方式，材质全用已锚定的名字、`deepseek_api_key=""` 强制离线，秒级跑完，适合日常快速验证。`scenarios/drift_push.py` 专测上面这条"必须搬一个正在动的障碍物"。`scenarios/warehouse_dynamic.py` 是同一机制在大型仓储场景下的验证，跑起来慢得多。

### SE(2) 路径规划器（`se2_planner.py`）

为障碍物规划一条连续的 SE(2) 路径，从当前位姿挪到不再挡路的位姿。

- **构型空间**：`se2_cell=0.15m` 平移网格 × `se2_n_theta=12` 角度层。用 Minkowski 和算每个角度层对每面墙的 C-障碍物。状态数上限由适配层把关（`manipulation._resolve_cell`：超过 `_MAX_SE2_STATES=200000` 就自动放大 cell）
- **Dial-bucket Dijkstra**：平移边按轴/对角/马步分级（990 / 1400 / 2214），旋转边权重基于障碍物平均旋转半径
- **提前终止**：按走廊范围自动限制搜索半径，障碍物不可能到的远端不再扩展
- **落点偏好**：`_forward_bias` 倾向把障碍物放到远离机器人的一侧，避免推到身后挡住来路

### 自适应旋转扫掠体（`manipulation.py — swept_between`）

扫掠体是碰撞检测的依据：把 A→B 插值成若干中间位姿，相邻两个取凸包再并起来。

问题出在旋转：凸包用**弦**近似旋转扫出的**弧**，中间那块"膨出"被漏掉了，而漏掉的正是**真实会扫到、检测却认为空着**的区域——假阴性，规划期说安全、执行期擦碰。

```
bulge = R × (1 − cos(Δθ/2))        R = ½√(l²+d²)
```

膨出与物体尺寸成正比，所以角步长按尺寸**反比**缩放：

| 障碍物 | 半对角 | 自适应 Δθ | 固定 15° 的膨出 | 自适应后 |
|---|---|---|---|---|
| 0.7×6.0（corridor 长板） | 3.02 m | 2.48° | **25.8 mm** | 0.71 mm |
| 2.0×2.0 | 1.41 m | 5.30° | 12.1 mm | 1.51 mm |
| ≤0.5 m 的小件 | ≤0.5 m | 15°（封顶） | 4.3 mm | 4.3 mm |

小物体保持粗步长不浪费算力，长条形自动加密。

**接触容差** `geometry.CONTACT_AREA_EPS = 1e-6`（约 1 mm²）：相交面积小于它才判"未碰撞"。纯粹吸收凸包近似和浮点残差，不是真允许 1 mm² 的物理重叠。

> 这个常量**规划期和执行期必须共用**。曾经规划用 1e-6、执行用 1e-9，中间那条带子里规划说能走、执行判撞上，方案会被 `failed_moves` 永久拉黑。

### 接触式搬运模型（`contact.py`）

**握持工位**：机器人是半径 0.3 m 的圆盘，与矩形相切时圆心落在矩形的**等距偏移曲线**上——4 条直边 + 4 段四分之一圆弧，周长 `2(l+d)+2πr`。沿弧长按 `contact_station_spacing=0.3m` 采样出 K 个候选握持点（夹在 8–64）。

工位定义在**障碍物局部坐标系**里，所以障碍物平移旋转时工位跟着动——障碍物原地转 90°，机器人就被带着绕它走一段弧，这段弧照样计距离。

**为什么是 DP**：SE(2) 路径有 T 个子步，每步选一个工位，就是在 `T×K` 格点上找最短路。三条约束：

1. 每个 (子步, 工位) 机器人圆盘不能压到墙或别的障碍物
2. 握持点只能沿表面**连续滑动**，单步最多滑 `contact_max_slide=0.6m`，且滑过的每个中间工位都得可行
3. 代价 = 机器人相邻两步的欧氏距离之和

转移用 `np.roll` 向量化，`O(T·m·K)`，一条路径几毫秒。

**绕到另一侧**：把首末位姿各复制 `pad=⌈K/2m⌉` 份接在路径两端，就得到"障碍物不动、机器人绕着它走"的前后两段。要拉的时候机器人得先走到另一侧，这段绕行由 DP 自然给出——不需要单独的绕行规划器。

**进出场**：从路网参考点直线开到第一个握持点，结束后直线开回。两段都要求整条线段机器人不压墙、不穿过其他障碍物。检测时两端各裁掉一个 `robot_radius`——端点本来就是已验证能占的位置，最后那一个半径是"贴上去"的对接动作。

> **一个必需的例外**：路网参考点可能正好在被搬障碍物的脚印**底下**（路网只按静态墙体建，不知道可移动障碍物在哪）。那是个名义位置而非机器人真能站的地方，此时连线检测无意义，跳过。不跳过的话，被挡住的边其中点几乎总在障碍物下面，所有搬运方案都会被"够不到任何握持点"否掉。

**参数**：

| 参数 | 默认 | 作用 |
|---|---|---|
| `contact_station_spacing` | 0.3 m | 握持点采样间距 |
| `contact_max_slide` | 0.6 m | 单子步最多滑多远。换算成工位数时**向下取整**，否则实际滑动会超设定值 |
| `contact_clearance` | 0.01 m | "贴住"与"压进去"的判定容差 |

**方向偏好 ≠ 方向限制**：`manip_forward_penalty=2.0` 只是软偏置，倾向把障碍物放到机器人前方（免得挡住回头路），不禁止任何方向。真正禁止的只有"不许把上次挪过的障碍物往回挪"（防振荡）。

### 感知（`perception.py`）

- **可见性**：障碍物轮廓 4 条边各切 2 段共 8 条半边，每条取首/中/尾 3 点；**同一条半边 3 点全通视**才算可见
- **墙体遮挡**：视线离开静态自由空间即被挡
- **高度判据——矮的挡不住高的**：遮挡物高度 ≤ 目标一半时直接跳过，因为目标露出的上半部分仍然可见

  ```
  robot ──────────►  ┌────┐   ← 高目标的上半部分照样看得见
            ┌──┐     │    │
  ──────────┴──┴─────┴────┘
             矮遮挡物      高目标
  ```

  这是 `h` 参与感知的唯一位置（另一个用途是算体积进 difficulty）。`see_over_short` 场景专门测它
- **交互揭示**：搬运本身就是接触，被搬的障碍物在开始前无条件揭示真值。不能出现"已经把东西挪走了却仍不知道它有多难挪"的状态

### 难度估计（`llm_difficulty.py`）

```
difficulty = (μ·ρ) × V × g        g = 9.81
```

- **μ** — 与地面的摩擦系数。带轮子的用等效滚动阻力（0.02–0.05），这是推车特别好推的原因
- **ρ** — **堆积密度** = 总质量 / 包围盒体积，**不是**原材料密度。货架里大半是空气，所以 `steel_shelf` 的 ρ 只有 300 而非钢的 7850；只有 `concrete_block` 这种实心体才用材料本身的 2400

代码里 μ 和 ρ 分开建表，`MATERIAL_MU_RHO` 由二者相乘生成——估计器和 LLM 都只处理 μ·ρ 这一个**尺寸无关**的系数。

- **锚点表**：22 个锚点材质 + `unknown` 兜底 + 12 条同义词。材质名精确命中时**直接查表，根本不调 LLM**
- **LLM 路径**：不在表里才请求 DeepSeek；prompt 给出完整锚点表并要求分别推理 μ 和 ρ 后相乘。失败自动回退启发式
- **缓存**：按 oid 缓存 difficulty，按材质名缓存 μ·ρ，同材质只问一次

完整材质表见[附录](#附录材质锚点表)。

### 性能优化

1. **跨 cycle 持久化搬运方案缓存**（`search.py`）：同一障碍物在同一条边上的方案跨重规划复用，实测命中率 ~70%
2. **Dijkstra 提前终止**（`se2_planner.py`）：按走廊范围限制搜索半径
3. **KDTree** 最近邻（`roadmap.py`）替代线性扫描
4. **STRtree** 空间索引（`executor.py`）：搬运每步碰撞检测 O(N) → O(log N)
5. **自适应旋转扫掠体**：既是精度手段也是性能手段
6. **扫掠体 AABB 粗筛**：精确相交前先比包围盒
7. **接触判定向量化**（`contact.py`）：`T×K` 个点合并成两次 `shapely.contains_xy` 调用；膨胀过的"其他障碍物"几何按 WKB 内容寻址缓存

### 接触模型带来了什么

> **历史存档，不可复现**：下表是当初引入"机器人必须贴身护送"这条规则时，拿它和一个
> "障碍物自己走、机器人原地等"的旧模型做的一次性对照实验，用来证明这条规则确实改变
> 了决策，不只是多记一笔账。2026-08-21 起旧模型（`--no-contact`）已经从代码里彻底
> 删掉——贴身护送是唯一模型，没有开关，这张表**没法重新跑出来**，只留结论存档。
> 数字本身还叠加了转弯能耗并入 J（同一天）的影响，两边都过期了（`corridor` 场景：
> 14637.36 → 16065.7817，见「两个必须知道的边界」）。

λ=350，`normal` 策略，8 次运行全部成功（旧模型仍存在时测的）：

| 场景 | 旧模型(`--no-contact`) J | 贴身护送 J | 其中搬运行程 | 涨幅 | 搬走的障碍物 |
|---|---:|---:|---:|---:|---|
| `corridor` | 13588.39 | 14637.36 | 1048.97 | +7.7% | [1] → [1] |
| `see_over_short` | 6852.36 | 7765.75 | 851.90 | +13.3% | [1] → [1] |
| `hidden_obstacle` | 40335.10 | 42629.65 | 1754.48 | +5.7% | [2,3] → [2,3] |
| `two_doors` | 7154.50 | 12980.69 | 206.35 | +81.4% | [1,2] → **[1]** |

- `corridor` 和 `see_over_short` 是**纯记账差异**：W 和 replan 次数一字不差，决策没变，多出来的就是机器人自己走的路——正好证明新增项确实只是"以前没算的账"
- `two_doors` 是**决策真的变了**：去够第二个障碍物不划算了，机器人改成只搬一个、多走点路。W 从 154.50 掉到 10.12，λD 从 7000 涨到 12970
- **代价**：接触规划让规划耗时涨 2–4 倍（two_doors 2.35 s → 16.08 s）

### 时间权重的实测对照

> **同样过期**：转弯能耗并入 J 之后，`w=0` 那一档不会再是表里这个数字了——`corridor`
> 场景的实测是加之前 `w=0/0.5/1` 三档 J 不一致（w=0 更差），加之后**完全一致**，`w=0`
> 现在会直接收敛到原来只有 `w>0` 才找得到的方案，见「两个必须知道的边界」。这张表还
> 没在 `two_doors` 上重新跑过，"`w=0.25` 那行只是转弯少了"这条结论目前意义变了——
> 转弯现在任何 `w` 下都计入 J，不会再出现"J 一样、纯因为转弯少而省时间"这种情况了。

`two_doors`，λ=350，`normal`，只改 `w`。J 与 `Robot motion time` 都是**执行期实测**，不是规划器的估计：

| `w` | J | 实测运动时间 | 搬走的障碍物 | A\* 展开 |
|---:|---:|---:|---|---:|
| 0 | 12,980.69 | 103.54 s | [1] | 41,495 |
| 0.25 | 12,980.69 | 95.73 s | [1] | 67,363 |
| 0.5 | 10,942.93 | 61.03 s | [] | 86,742 |
| 0.75 | 10,942.93 | 61.03 s | [] | 94,973 |
| 1 | 10,971.56 | **60.99 s** | [] | 104,208 |

- **单调有效**：时间降 41%，代价是 A\* 展开数涨 2.5 倍（规划变慢）
- `w=0.25` 那行很说明问题（**转弯能耗并入 J 之前**的现象，现在不会再出现，见上方过期提示）——当时 J、搬的障碍物、路线全没变，只是转弯少了，就省下 7.8 s
- `w≥0.5` 后机器人干脆不搬了：绕路虽然多走 3.4 m，但省掉了"贴着爬 0.25 m/s + 抓放 4 s"

### 接触约束是硬的

对四个场景规划期产生的全部 **139 条接触轨迹**逐点核对四条不变量，全部通过：

1. 障碍物移动的每个子步，机器人到障碍物的距离**恰好** = `robot_radius`（误差 <1e-6 m）——既没脱手也没压进去
2. 机器人圆心始终在 `free_eroded_tol` 内、且不在其他障碍物膨胀域内
3. 握持点单步位移不超过"质心位移 + 旋转带动 + `contact_max_slide`"——手是滑过去的，不是瞬移的
4. 报告的 `travel` 等于轨迹折线实际长度

**执行期也核对过**：四个场景每个真实搬运子步结束时距离全部**精确 0.300000000 m**。

> 量的时候必须在障碍物和机器人**都**更新完之后——一个子步是两次写入，量在中间只会读到写了一半的状态。

这套核对抓出过一个真实缺陷：SE(2) 规划器的朝向按模 π 存储（矩形转 180° 脚印相同），直接拿存储角算握持点，会在角度索引从 π 绕回 0 时把机器人**瞬移到对面那一侧**。修法是用 `wrap_dtheta` 累积连续朝向。

**已知界限**：接触在每个子步的**端点**上精确；子步**内部**机器人走直线插值，而真实保持接触的运动在旋转时是圆弧，存在 `grip_radius × (1−cos(Δθ/2))` 量级的瞬时偏差——`se2_n_theta=12` 下 corridor 那块长板最大约 28 mm。与扫掠体膨出是同一类离散化残差，调大 `se2_n_theta` 可收紧。

### LLM 估计精度

```bash
cd CA-NAMO
python bench/llm_accuracy.py accuracy   # 打 API 测 61 个物体（约 200 次调用）
python bench/llm_accuracy.py nav        # 估计误差对导航代价的影响（不打 API）
python bench/llm_accuracy.py report     # 只重新生成报告和图
python bench/llm_accuracy.py all        # 全跑
```

产物在 `bench/llm_test_out/`。**当前配置（开推理、不限 token）：典型误差 1.37×、84% 落在参考值 2× 以内、Spearman 0.97。**

这是 2026-08-10 修掉一个严重缺陷后的结果。修之前（`thinking: disabled` + `max_tokens: 32`）估计器**根本没在估计**：

| | 旧（无推理，32 token） | 新（开推理，不限） |
|---|---|---|
| 典型误差 / 2× 内 / Spearman | 6.14× / 23% / 0.47 | **1.37× / 84% / 0.97** |
| 表外物体照抄锚点表某一行 | 92% | 23%（且这 23% 是对的） |
| 塌缩到单一值 1440 | 46% | 2% |
| 61 题产生的不同数值 | 16 | 51 |
| 单次调用耗时 | ~0.2 s | ~45–70 s |

- **决定性证据**：把 prompt 里锚点表的**行序打乱**（其余逐字节不变），39 个表外物体的答案成批地从 1440 变成 350、再变成 174——答案由**排版**决定而不是由物体决定。这也否掉了"末行效应"和"最大值效应"两个直觉解释。重排不是解药，只是把塌缩点挪个位置
- **根因是请求参数不是模型**：换 `deepseek-chat` 结果几乎一样。prompt 要求多步推导，32 个 token 装不下，模型就退化成对表做模式匹配
- **旧配置下离线启发式反而更准**（2.4×／41%），即"调 API 让估计变差"
- **仍未解决**：μ·ρ 按定义与尺寸无关，但实测有系统性泄漏——同一物体 ×0.5／×1／×2 缩放下答案最大差 2.0×，越大给的密度越低。偏差全在容差带内，但确实存在
- **代价**：温度 0 下可复现性从 97% 降到 16%（中位离散 1.25×）。按材质缓存，所以单次运行内自洽，差异只在不同次运行之间

### 估计误差对结果的影响

- **容差带很宽**：全部估计统一乘 0.25×–4×，四个场景的 J **全部不变**——决策离平衡点足够远，这个范围内的误差是免费的
- **两侧失效方式不对称**：严重低估（×0.05）代价最大（hidden_obstacle +35.6%、maze_mixed +58.9%，以为轻、搬下去才发现重）；严重高估（×8–20）只让它放弃本该搬的障碍物改绕路（+7.8%）
- **按实测误差分布做 20 次随机复现**：当前估计器**平均 +0.0%、最坏 +0.0%**。修复前是平均 +3.4%、最坏 +51.9%——差别不在均值而在尾部，修复把重尾整个消掉了
- **没有普遍安全的 λ**：two_doors 在 λ≤350 时平均 +13%／最坏 +52%，λ≥700 归零；maze_mixed 恰好相反

### 正确性保证

- **账目是准的**：W 恒用真实 difficulty 结算，与估计准不准无关。任何物理接触都会把真值写进 belief
- **搜索在当前信念下最优**：g 值来自真实几何算出的距离，h 是可采纳下界
- 这里的"最优"指**在机器人当前知识下**的最优，配合持续重规划——不是一次性全局最优（障碍物几何先验未知，这符合问题定义）

## 可视化说明

**汇总图**：终态 + 机器人轨迹走廊 + 障碍物初始位置（红色虚线）。轨迹走廊包含搬运时绕过去的那几段，能直接看出机器人为搬东西多走了多少。

**过程动图**：每个事件一帧。**黄色圆盘是机器人的真实位置**——搬运期间它贴着障碍物一起动，不再停在路网节点上。

| 颜色 | 含义 |
|---|---|
| 黄色圆盘 | 机器人 |
| 蓝色实线 | 规划的行驶路线 |
| 蓝色虚线 | 规划的障碍物路线 |
| 深黄点线 | 规划的握持轨迹 |
| 橙色 / 红色 | 已搬动 / 未搬动的障碍物 |

障碍物标签是三行：`oid` / `est=…`（估计值）/ **对估计的判定**。第三行只在机器人真碰过之后才出现——估对了写 `right`，估错了才写 `real=…` 给出真值。所以扫一眼就知道估错了哪些、错到什么程度，估对的不占版面。碰之前只有前两行；没估过就直接碰上的（撞出来的），只有 `real=…`。

每帧停留时长按相邻帧的仿真时钟差值折算（不含 `plan_time`），不是固定帧率——一次缓慢的贴身搬运在动图里就该看着比一步快速挪动更慢。

| 参数 | 默认 | 作用 |
|---|---|---|
| `gif_speed` | 1.0 | 播放速度倍率，相对仿真时间；1 = 原速，越大越快 |
| `gif_fps` | 5.0 | 单帧最短停留对应的帧率上限，避免极短子步一闪而过 |
| `gif_max_frame_s` | 5.0 | 单帧最长停留秒数，避免一次缓慢搬运把动图卡住半天 |
| `gif_end_hold_s` | 2 | 末帧停留秒数 |
| `gif_dpi` | 300 | 每帧分辨率。标签只有 7pt，低于 100 会糊 |

> 全部帧共用一张调色板，Pillow 因此只存帧间差异。路网背景每帧都重画且完全相同，不共享调色板文件会大 20 倍以上（maze_doors 实测 0.38 MB vs 8.6 MB）。
